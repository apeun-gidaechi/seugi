# Mobile screen parity audit

The native projects have separate route destinations, while the TypeScript mobile app intentionally combines some destinations into step-based screens. A mapped target means a corresponding UI path exists; it does **not** mean that visual and device behavior parity has been verified. Rows marked `device QA pending` still need comparison on Android and iOS.

## Screen inventory and audit limits

- The authenticated TypeScript shell currently wires 26 logical destinations: five bottom tabs, the chat conversation view, and 20 detail destinations in `AppDetail`. The iOS `MainDestination` enum has 21 cases, plus five tab roots; the Android `MainScreen` graph declares 25 destinations over 24 distinct route bases (notification create/edit share a base). These counts describe navigation entry points only, not independent full-screen implementations or parity.
- There are 36 production Android `*Screen.kt` files under `feature-*` and 36 TypeScript `.tsx` files under `apps/mobile/src/screens/`. This file-count match is incidental: Android includes screen files that TypeScript represents as nested modules, while TypeScript includes coordinators, shared shells, and overlays. Auth has four dedicated content screens coordinated by `AuthScreen`; workspace join and room creation also coordinate multiple steps, and image previews/member info are overlays. Thus a destination may exist without having the same independent screen boundary or presentation as native. Audit the navigation stack, full-screen vs modal presentation, and back transitions per original destination before treating it as converted.
- The Android onboarding graph declares `oauthSignUp`, but it has no inbound navigation call: the email-login callback goes directly to email signup, and the orphan screen's continue action is a no-op. ## Design-system conversion status

The native screen map above is not evidence that the UI layer is fully converted. The original Android design system contains reusable implementations for buttons, top bars, text fields, navigation, chat items/lists, avatars, dialogs, pickers, toggles, badges, loading/error states, and related modifiers. The iOS `Component` project has corresponding reusable controls plus iconography, gradients, shadows, typography, and modal/navigation helpers. Together these source trees contain over 100 component/foundation files.

The TypeScript mobile target has shared color/font tokens, 25 design-system modules under `apps/mobile/src/design-system`, shared UI primitives, and feature-specific components. The native UI is therefore partially converted, but inline screen styling and unported variants remain. Treat this as a remaining parity gap, not as an absence of a component library.
